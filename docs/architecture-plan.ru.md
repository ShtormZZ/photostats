# Архитектурный разбор и план развития photostats

Дата: 6 ноября 2026 года. Версия: 1.15.0, текущее рабочее дерево, включая Directories и Timeline с раскрытием всех фотографий дня.

Статус: предложение к реализации. В рамках разбора программный код и рабочие данные не изменялись. Изменения схемы и `ANALYZE` проверялись только на временных копиях БД; сценарии сканирования — на созданных для проверки фотографиях.

## 1. Основные выводы

Существующую основу стоит сохранить: Python, Flask, SQLite, отдельные процессы сканирования и локальный веб-интерфейс. Измерения не показывают необходимости перехода на другую СУБД, ORM или обязательный frontend-фреймворк. Наибольшую пользу дадут исправления жизненного цикла данных, обслуживание планировщика SQLite и сокращение повторных вычислений.

Приоритеты:

1. Предотвратить потерю пользовательских данных при недоступности диска и устаревание метрик при изменении фотографии.
2. Ввести воспроизводимые проверки, единые миграции и явное закрытие соединений.
3. Обновлять статистику планировщика SQLite; отдельно оптимизировать статистику и дубликаты.
4. Разделить серверный код и JS по ответственности, сохранив поведение интерфейса.
5. Добавлять новые возможности небольшими самостоятельными релизами.

### Что уже сделано хорошо

- EXIF, анализ изображения и сигнатуры разделены на возобновляемые проходы; результаты записываются пакетами.
- WAL и ожидание блокировок позволяют серверу читать данные во время сканирования.
- Пользовательские оценки и комментарии отделены от полей, которыми владеет сканер; нормализация тегов и правило дубликатов вынесены в общие модули.
- Фильтры параметризованы, поля сортировки выбираются из разрешённого списка. Диаграммы сохраняют семантику исключения собственного фильтра.
- Directories строит дерево из одной агрегированной выборки, без запроса на каждый каталог.
- Timeline уже использует порции дней, облегчённые записи фотографий и виртуализацию. Раскрытый день также виртуализирован и загружается порциями.
- Есть сквозной smoke-тест и CI для Windows/Linux, Python 3.10/3.12.

### Что обязательно сохранить

- Локальную обработку фотографий; подключение внешней карты только по действию пользователя.
- Оценки, комментарии и теги при обновлении EXIF, алгоритмов анализа, миграциях и переносе архива.
- Существующие правила дубликатов, Unicode-нормализации тегов и фильтрации диаграмм.
- Раздельные версии EXIF, цвета и резкости; изменение декодирования цвета требует проверки совместимости результатов.
- Независимость Timeline от фильтров Statistics. Уточнение от 13 ноября 2026: собственные теги (хотя бы один), режимы всех/хороших/5+ оценок и отдельное добавление фото без оценки. Независимый переключатель 15 per day ограничивает вывод после всех фильтров; Show all раскрывает все подходящие фото, если их больше 15. Без ограничения все подходящие кадры показываются порциями независимо от флажка без оценки. Новые параметры не сохраняются после перезагрузки. Analyse day открывает весь день.
- Ручной Refresh в Directories. Автоматическое обновление дерева в этот план не входит.
- Ограничение Open/Reveal локальным режимом и отсутствие автоматического удаления оригиналов.

## 2. Подтверждённые наблюдения

### Объём и методика

Просмотрены `scan.py`, `app.py`, `launcher.py`, `jobs.py`, `tags.py`, `dupkey.py`, `web/index.html`, тесты, зависимости и CI. Размер основных файлов: `scan.py` — 1 980 строк, `app.py` — 1 603, `web/index.html` — 3 487, `launcher.py` — 674.

В рабочей БД на момент проверки: **132 761 фотография, 778 значений каталога, 3 211 значений календарной даты**, максимум 2 582 фото за день. Файл БД — около 108,2 MiB, WAL — около 40,5 MiB. В `photos` — 23 явно созданных индекса и один автоматический UNIQUE-индекс. `sqlite_stat1` отсутствует; свободных страниц по `freelist_count` — 0. Сам размер WAL не доказывает неисправность, оснований для срочного `VACUUM` эти данные не дают.

Измерения выполнены через Flask test client, Python 3.12.7 / SQLite 3.45.3. Соединения заменены на `mode=ro` + `query_only`; миграции сервера не запускались. Для каждого основного сценария сделано три последовательных запроса. Это ориентировочный серверный замер, **не p95**, не замер браузера, сети или создания миниатюр; файловый кэш ОС не сбрасывался. ### Эксперимент с планировщиком

В текущей БД поиск следующего дня Timeline использовал `MULTI-INDEX OR` по `ix_rating` и временную сортировку. Один запрос: около 101 мс. В разовом эксперименте принудительный `ix_taken` дал около 0,11 мс. Это диагностический эксперимент, а не предложение повсеместно прописывать `INDEXED BY`.

БД скопирована через SQLite backup API. **На одной и той же временной копии**, с одинаковым запросом и seed, получено:

| Состояние копии | Timeline, первые 8 дней, мс |
|---|---:|
| До `ANALYZE` | 1 416,3 / 1 379,2 / 1 385,1 |
| После `ANALYZE` | 3,6 / 3,8 / 3,2 |

После анализа план использует `ix_taken`. Сравнение внутри одной копии исключает разницу между дисками исходной БД и временного каталога. Результат относится к этому архиву и запросу; его нельзя переносить на все фильтры. Дополнительная проверка Statistics на проанализированной копии всё ещё дала 2,38–3,37 секунды.

`ANALYZE` собирает статистику распределения данных для планировщика. Политика `PRAGMA optimize` зависит от версии SQLite: ограничения времени работы были изменены в 3.46.0, а в проверенной среде — 3.45.3. Это нужно учесть в реализации. [Документация SQLite](https://www.sqlite.org/lang_analyze.html).

### Конкретные проблемы

| Код | Наблюдение и основание | Последствие |
|---|---|---|
| R1 | `scan.py:exif_pass()` формирует `gone` из всей БД, затем удаляет записи по `not os.path.exists()` | Недоступный диск вне текущих корней сканирования может потерять записи вместе с оценками, комментариями и тегами |
| R2 | При обновлении файла UPSERT меняет EXIF-поля, но сохраняет `sig`, цвет и резкость | После замены содержимого по тому же пути результаты анализа и определение дубликатов могут стать неверными |
| R3 | `with db() as con` в большинстве старых обработчиков не вызывает `close()` | Освобождение соединений зависит от сборки мусора; лишние ресурсы и труднее управлять чтением/записью |
| R4 | `api_stats()` вызывает множество помощников, каждый со своим соединением | 26 соединений и 30 SELECT; диаграммы одного ответа могут читать разные состояния архива |
| R5 | `derived_counts('dup')` повторяет подзапрос групп дубликатов в ветвях CASE | В одном профиле интервал выполнения этого запроса составил около 1,1 секунды; это основной кандидат на переработку |
| R6 | Миграции колонок и часть индексов дублируются в `scan.py` и `app.py` | Поведение зависит от того, какая программа первой встретила старую БД |
| R7 | Числовые и диапазонные параметры проверяются неодинаково | `limit=oops` и `size=oops` дают 500; `limit=-1` принимается и снимает SQL-ограничение числа строк |
| R8 | `api_thumb()` пишет прямо в конечный файл, `raw_preview()` не задаёт timeout | Одновременные запросы могут читать незавершённый кэш; зависший ExifTool способен надолго занять обработчик |
| R9 | Большие списки задач сканера и CSV целиком собираются в памяти | Рост потребления памяти вместе с размером архива; требуется отдельный нагрузочный замер |
| R10 | HTML/CSS/JS и состояния трёх страниц находятся в одном файле | Изменения навигации, карточки и загрузки легко затрагивают соседние страницы |
| R11 | Виртуализация удаляет DOM, но `days`, `allItems`, `allById` сохраняются до Refresh | Память длительной сессии может расти с числом просмотренных фото; фактический рост ещё не измерен |
| R12 | `ask()` вызывает `r.json()` без общей проверки HTTP-статуса; очередь миниатюр последовательная | Неоднородная обработка ошибок; медленная миниатюра задерживает последующие |
| R13 | Smoke-проверка `page served` содержит `or True`; тест лицензии ищет фразу без учёта переноса строки | Одна проверка всегда успешна; другая блокирует последующие шаги CI ложным срабатыванием |

R1 воспроизведён на временном архиве: после недоступности второго каталога сканирование первого удалило запись второго и её тег. Оригинальный файл в тесте оставался в переименованном каталоге. R2 также воспроизведён: размер и mtime обновились, прежние сигнатура, цвет и версия резкости сохранились. Это подтверждает механизм ошибки, но не означает, что в рабочем архиве уже потеряны данные.

Поведение контекстного менеджера SQLite проверено отдельно: после выхода из `with` соединение остаётся пригодным для запросов. Документация прямо разделяет управление транзакцией и закрытие соединения. [Python 3.12: Connection context manager](https://docs.python.org/3.12/library/sqlite3.html#how-to-use-the-connection-context-manager).

Планы запросов Directories и фильтра каталога показывают полный просмотр `photos`; группировка дополнительно использует временное дерево. Это основание для эксперимента с индексами, но при нынешних 250–260 мс не основание срочно заводить отдельную таблицу агрегатов.

### Проверки и ограничения аудита

- `tools/smoke_test.py`: все проверки прошли.
- `tools/check_license.py`: ошибка поиска фразы, которая в `LICENSE` разбита переводом строки; после нормализации пробелов фраза находится. Это дефект проверки, а не заключение о юридической действительности лицензии. `LICENSE` не изменялся.
- Профиль SQL через trace callback измеряет интервалы между запросами, включая получение строк и небольшой объём Python-работы; это не чистый CPU-профиль SQLite.
- В этой проверке не измерены браузерные FPS/heap, холодные RAW-превью, скорость сканирования полного архива и нагрузка нескольких клиентов. Для них ниже предусмотрен отдельный стенд.
- Локальные диагностические JSON находятся в игнорируемом `cache/architecture-*.json`. Они не входят в воспроизводимый CI; приведённые выше результаты сохранены непосредственно в документе.

## 3. Целевая структура

Предлагается постепенное выделение модулей при сохранении существующих CLI и URL:

```text
app.py / scan.py / launcher.py       — совместимые точки входа
photostats/
  db/                               — соединения, миграции, обслуживание
  domain/                           — рейтинг, теги, даты, дубликаты
  queries/                          — фильтры, статистика, каталоги, Timeline
  services/                         — миниатюры, экспорт, сканирование
  http/                             — маршруты, проверка входа, ответы
web/
  index.html
  css/
  js/
    api.js, router.js, state.js
    pages/                          — statistics, directories, timeline
    components/                     — карточка, рейтинг, теги, миниатюры
tests/                              — модульные, интеграционные, браузерные
tools/                              — smoke, benchmark, диагностика
```

Это ориентир ответственности, а не требование создать все каталоги сразу. Каждый модуль выделяется вместе с проверкой своего поведения. В первой итерации достаточно отдельных CSS и ES modules, обслуживаемых Flask, без обязательной сборки. Общая карточка фотографии должна получать контекст коллекции явно, а не определять его по глобальному состоянию страницы.

## 4. ТЗ: оптимизация Python-кода

Приоритеты: **P0** — сохранность и корректность данных; **P1** — следующий технический релиз; **P2** — после стабилизации. Размер: **S** — локальная задача, **M** — несколько модулей, **L** — изменение жизненного цикла с миграцией/регрессией. Это относительная сложность, не обещание календарного срока.

### CODE-01. Безопасная сверка файлов — P0 / M

**Основание:** R1, `scan.py:exif_pass()`, `walk_photos()`.

**Работы:** ограничить сверку файлами внутри явно выбранных корней; учитывать ошибки обхода через `os.walk(onerror=...)`; отличать отсутствие файла от недоступности корня и ошибки доступа. При неполном обходе сохранять прежние записи. На первом этапе полностью отключить автоматическое удаление записей по одному отрицательному `exists()`. Ввести понятный результат «каталог недоступен / проверка не завершена». Долговременный статус отсутствующего файла — через DB-02, без удаления аннотаций.

**Приёмка:** недоступный диск B при сканировании A не меняет записи B; ошибка доступа и остановленный проход ничего не удаляют; возвращение диска восстанавливает доступ без потери ID, оценок, тегов и комментариев. Проверить обычный и `--full` проходы, корни-файлы, вложенные и пересекающиеся корни. **Зависимости:** защитное исправление автономно; постоянные статусы зависят от DB-02.

### CODE-02. Инвалидация результатов при изменении файла — P0 / M

**Основание:** R2, `scan.py:COLUMNS`, UPSERT в `exif_pass()`, `NEEDS_COLOUR`, `NEEDS_SHARP`.

**Работы:** различать перечитывание неизменного файла из-за версии EXIF и изменение его файлового отпечатка. При обнаруженном изменении размера/mtime инвалидировать сигнатуру и все связанные метрики цвета/света/резкости; следующие проходы должны пересчитать только необходимое. Сохранить пользовательские поля и ID. Для режима `--full` тоже загружать прежний отпечаток, чтобы не смешивать эти причины пересканирования. Изменения с полностью сохранёнными размером/mtime обнаруживаются отдельной проверкой содержимого, не обещать их обнаружение дешёвым проходом.

**Приёмка:** замена JPEG по прежнему пути меняет сигнатуру и метрики после проходов; EXIF_VERSION на неизменном файле не обнуляет анализ; `mark/comment/tags` сохраняются в обоих случаях; частичный сбой анализа остаётся видимым как незавершённый/ошибочный результат. **Зависимости:** CODE-06; схема статусов при необходимости через DB-02.

### CODE-03. Явный жизненный цикл соединений — P1 / M

**Основание:** R3–R4, `app.py:db()`, `counts()`, `bucket_counts()`, `api_stats()`.

**Работы:** единая фабрика соединений; одно соединение на обычный HTTP-запрос с гарантированным закрытием в teardown. Функции запросов принимают соединение явно. Согласованный многозапросный ответ читается в короткой явной транзакции; запись имеет явные commit/rollback. Переключение journal mode выполнять при инициализации, сохранив настройку timeout на соединениях. Сканеру и heartbeat оставить отдельные соединения в соответствующих потоках/процессах.

**Приёмка:** Statistics использует одно соединение; соединение закрывается после успеха, ошибки и отменённой выдачи; Windows позволяет закрыть/заменить тестовую БД сразу после завершения запросов; параллельный сканер не вызывает регрессии `database is locked`. Для потокового экспорта отдельно проверить закрытие при разрыве клиента. **Зависимости:** CODE-06.

### CODE-04. Границы модулей и контракт API — P1 / L

**Основание:** R6–R7, монолитные `app.py`, `scan.py`.

**Работы:** сначала выделить функции рейтинга/дат/фильтров и схемы, затем запросы страниц и сервисы. Разделить разбор HTTP-параметров и SQL. Общая проверка положительных limit, неотрицательных offset, дат, конечных чисел и диапазонов; верхние границы выдачи. Единый JSON ошибки `{error: {code, message}}`, корректные 400/404/409/500. Общая проекция краткой карточки и отдельный `GET /api/photos/<id>` для подробностей; сохранить старые маршруты до перехода интерфейса.

**Приёмка:** ошибочные параметры никогда не дают необработанный 500; отрицательный limit не снимает ограничение; результаты старых корректных фильтров совпадают по ID и агрегатам. Правила диаграмм `skip`, рейтинга и дубликатов имеют один источник определения. **Зависимости:** CODE-03, DB-02, CODE-06. Разбивать на небольшие изменения по одному модулю.

### CODE-05. Ограниченная очередь сканирования и понятный прогресс — P2 / L

**Основание:** R9, `sign_files()`, `analyze_colors()`, `exif_pass()`, `launcher.py:Task`.

**Работы:** обрабатывать задания ограниченными пакетами, без второй полной копии списка и неограниченной постановки futures. Отдельно измерить память словаря известных файлов; при необходимости заменить его временной таблицей сверки/порционной обработкой. Сохранить пакетные commit и предсказуемую остановку. Добавить машинный поток событий прогресса с версией протокола; launcher читает события, обычный текст остаётся для CLI. Исправить различение `failed` и `stopped`: сейчас `Task.finished()` любой ненулевой код отображает как stopped.

**Приёмка:** на 100 тыс. и 1 млн синтетических записей объём очереди ограничен конфигурацией; число реально выполненных файлов и прогресс совпадают; остановка сохраняет закоммиченные пакеты; повторный запуск продолжает проход. Производительность не хуже 90% исходной на том же наборе. Проверить зависший ExifTool и аварийный worker. **Зависимости:** CODE-01/02/06.

### CODE-06. Проверки и воспроизводимый стенд — P1 / M, начать первым

**Работы:** убрать `or True` из проверки страницы; исправить сравнение лицензионной фразы с учётом пробельных символов, не переписывая LICENSE. Отделить проверки алгоритмов, миграций и API от запуска всей программы, сохранив smoke как сквозной сценарий. Перенести нужные браузерные регрессии из локальных вспомогательных скриптов в отслеживаемые тесты CI. Зафиксировать проверенный набор зависимостей constraints-файлом и явно обновлять его.

**Приёмка:** намеренно неправильная страница проваливает тест; форматирование лицензии не вызывает ложного отказа; реальные отсутствующие обязательные фрагменты обнаруживаются. CI выполняет все шаги. Обязательные регрессии: CODE-01/02, фильтры и дубликаты, Directories Refresh/поиск, Timeline рейтинг/раскрытие/скролл/Back/ошибка сети/смена страницы. Benchmark создаёт синтетическую БД, выдаёт JSON с версиями, числом SQL, размерами ответов, median/p95; доступ к личному архиву для CI не нужен. **Зависимости:** нет.

## 5. ТЗ: оптимизация БД

### DB-01. Статистика планировщика — P1 / S, быстрый выигрыш

**Реализовано 13 ноября 2026:** обслуживание при запуске и после существенных
изменений архива, метаданные и `/api/db/diagnostics`. На копии 132 761 фото
Timeline: median 1 388,051 → 3,589 мс, p95 после — 3,871 мс; ответы при том же
seed совпадают. Рабочая БД не изменялась. Проверены пять синтетических
распределений; компромисс для 99% bad и границы проверки описаны в
[отчёте](database-maintenance.md#measurements-on-13-november-2026).

**Работы:** после миграций индексов и существенного пополнения архива выполнять обслуживание статистики в контролируемом процессе записи. Для уже существующей БД без статистики предусмотреть однократный запуск. Выбрать `ANALYZE`/`PRAGMA optimize` с учётом фактической версии SQLite; не запускать обслуживание внутри каждого GET. Хранить дату/версию последнего обслуживания, показывать результат в диагностике. Сначала проверить все основные запросы на копии.

**Приёмка:** Timeline на контрольном архиве использует эффективный поиск по дате; результат выборки при том же seed не меняется. Проверить распределения «почти все без оценки», «почти все bad», «много 5+», разреженные дни и большой отдельный день. Не допускается ухудшение median других базовых сценариев более чем на 10% без отдельно объяснённого компромисса. **Зависимости:** baseline из CODE-06; совместимо с будущим DB-02. Принудительные индексы — только при доказанной необходимости после этого этапа.

### DB-02. Единые версионированные миграции — P1 / M

**Реализовано 13 ноября 2026:** общий `db_schema.py` для app/scan/jobs, атомарные
нумерованные миграции, проверенная копия перед изменением непустой БД,
пересоздание изменившихся выражений индексов и транзакционный revision.
Проверены прежние схемы, порядок запуска, повторный запуск, одновременная
инициализация, сбой и восстановление копии с сохранением ID и аннотаций.
[Обслуживание и восстановление](database-maintenance.md).

**Работы:** один модуль схемы для app/scan/jobs; последовательность миграций с номером и результатом. Существующая БД распознаётся по фактической структуре и переводится на новую систему без пересканирования. Изменение выражения индекса приводит к его контролируемому пересозданию. Пакет миграции атомарен там, где это поддерживается операциями; долгие backfill имеют понятное восстановление после прерывания. Добавить журнал изменения данных/revision для будущего кэширования, обновляемый в той же транзакции, что и фото/аннотации.

**Приёмка:** свежая БД и несколько прежних схем сходятся к одинаковой структуре независимо от порядка запуска app/scan; повторный запуск ничего не меняет; симуляция сбоя допускает корректное продолжение. Сохраняются все ID и пользовательские поля. Одновременный запуск двух точек входа не оставляет полусхему. **Зависимости:** CODE-06; перед рискованной миграцией — механизм резервной копии DB-05.

### DB-03. Сокращение стоимости Statistics и дубликатов — P1 / L

**Работы:** сначала измерить каждый запрос отдельно. Переписать подсчёт групп дубликатов так, чтобы набор ключей вычислялся один раз для соответствующей выборки/снимка, а не в обеих ветвях CASE. Общие итоги архива отделить от итогов фильтра. Группировать совместимые агрегации только при одинаковом WHERE: исключение собственного фильтра диаграммы сохраняется. После SQL-оптимизации добавить ограниченный кэш по нормализованному фильтру, конфигурации и revision БД; не кэшировать ошибку или недостроенный результат. Проверить пользу ленивой загрузки дорогих панелей совместно с WEB-04.

**Приёмка:** суммы и состав каждой диаграммы полностью совпадают с эталоном, включая собственный фильтр, NULL, кириллицу и переход между правилами дубликатов. Изменение mark/tag/comment, новое сканирование или новый hash инвалидирует нужные результаты. Сравнивать первый запрос без кэша отдельно от повторного. Цель первой итерации — уменьшить median полного некэшированного Statistics минимум на 50%; если цель не достигнута, представить профиль остаточной стоимости. **Зависимости:** CODE-03/06, DB-02; проверять после DB-01.

### DB-04. Индексы, пагинация и экспорт по измерениям — P2 / M

**Работы:** составить карту «индекс → запросы → цена записи/размер». Проверить `folder` и его collation для точного и вложенного поиска, сортировки по рейтингу/резкости и глубоких страниц. Сравнивать планы и время на копии до/после, не добавлять индекс на каждый фильтр. Для хронологического списка и раскрытого дня рассмотреть курсор `(taken, id)` вместо глубокого OFFSET; определить реакцию на изменение revision между порциями. CSV отдавать порциями, обеспечив согласованность выгрузки и закрытие ресурсов при разрыве клиента.

**Приёмка:** страницы неподвижной БД не теряют и не дублируют ID; при изменении архива интерфейс явно обновляет выборку, а не смешивает снимки. Проверить NULL, одинаковые taken, оба направления, literal `%/_/!` в путях и кириллицу. Индекс включается только при выигрыше целевого сценария и приемлемой цене сканирования. Экспорт большого набора не создаёт несколько полных копий результата в памяти; формат CSV и Unicode сохраняются. **Зависимости:** CODE-04/06, DB-01/02.

### DB-05. Резервные копии и обслуживание — P1 / M

**Работы:** сервис согласованной копии через SQLite backup API; проверка копии и запись версии схемы. Восстановление при остановленных писателях, с сохранением предыдущей БД для отката. Диагностика размера DB/WAL, свободных страниц, версии SQLite, последнего обслуживания. Политику checkpoint проверять при одновременном сканировании; освобождение места запускать по необходимости, не при каждом старте. Копия каталога должна явно отличаться от резервной копии самих оригиналов.

**Приёмка:** копия во время сканирования открывается и проходит проверку целостности; восстановление возвращает ID, оценки, комментарии и теги; сбой копирования не повреждает исходник. После восстановления нет старых несовместимых WAL/SHM от заменённой БД. Пути/EXIF не уходят во внешние сервисы. **Зависимости:** CODE-06; версия схемы интегрируется с DB-02.

### WEB-01. Разделение страниц, состояния и запросов — P1 / L

**Работы:** вынести CSS и JS в модули по целевой структуре. Состояния Statistics, Directories, Timeline сделать отдельными; общими оставить только карточку и сервисы. Общий API-клиент проверяет HTTP-статус, разбирает JSON ошибки и поддерживает отмену группы запросов при уходе со страницы/Refresh. Сохранять проверку generation/revision даже после abort. Маршрутизация владеет history, фокусом и восстановлением прокрутки; восстановление не должно перезаписывать новый пользовательский скролл.

**Приёмка:** смена страницы во время загрузки не обновляет скрытую или новую выборку; Back/Forward возвращают положение и раскрытые дни; Refresh меняет seed только по текущим правилам. Нет двойных обработчиков и необработанных Promise rejection. Переход из Directories сохраняет текущую семантику фильтров, из Timeline — анализ всего выбранного дня. **Зависимости:** CODE-04/06. ### WEB-02. Миниатюры: приоритеты и надёжный кэш — P1 / M

**Работы:** измерить очередь и сравнить ограниченную параллельность 1/2/4 с приоритетом видимых фото и открытой карточки. Удалять устаревшие задания; предусмотреть timeout, повтор и понятный placeholder. На сервере объединять одновременную генерацию одного ключа, писать временный файл и атомарно публиковать готовый JPEG. Ввести ограничение времени ExifTool и допустимого числа декодирований. Версионировать ключ превью при изменении файла/алгоритма и передавать эту версию в URL, чтобы браузер не показывал старое фото по прежнему `/thumb/id`. Добавить лимит дискового кэша и обслуживание вне критического пути GET.

**Приёмка:** два клиента не получают частичный JPEG; зависший RAW не останавливает всю очередь; после замены фото показывается новая миниатюра без Ctrl+F5. Видимые фото не ждут длинную очередь скрытых, фильтры остаются отзывчивыми. Выбрать параллельность по замерам на JPEG и RAW, а не заранее назначить максимум. **Зависимости:** CODE-02/03/06, WEB-01 для группы отмены.

Ввести бюджет для метаданных дальних дней и полных карточек; вытеснять данные с возможностью повторной загрузки, сохраняя seed, размеры секций и якорь прокрутки. Для Directories проверить поиск и раскрытие 10 тыс. узлов: добавить debounce и виртуализацию строк только при подтверждённой задержке. Для списка Statistics определить предел накопления DOM при многократном Load more.

**Приёмка:** на синтетических 10 тыс. фото в одном дне и 10 тыс. дней количество DOM-фотографий ограничено видимой областью с запасом; после нескольких циклов прокрутки память выходит на плато в установленном бюджете. Возврат к выгруженному дню сохраняет подборку и положение. Нет пустых областей из-за неверной высоты или потерянного запроса. **Зависимости:** WEB-01, CODE-06. Для дорогих невидимых/свёрнутых панелей предусмотреть отложенный запрос с отдельным состоянием ошибки и Retry. Клавиатурная навигация по дереву и фото, видимый фокус, доступные названия кнопок, корректный возврат фокуса из карточки. Проверить большие подписи дат/года и кнопку раскрытия на узком экране. Поддержать уменьшение анимации по настройке пользователя.

**Приёмка:** ошибка одной панели не очищает остальные; устаревший ответ не подменяет новые фильтры. Все основные действия доступны без мыши; после раскрытия/закрытия дня и карточки фокус остаётся предсказуемым. На ширинах 360/768/1440 px нет перекрытий элементов управления и горизонтального скролла всей страницы. **Зависимости:** WEB-01, DB-03, CODE-06.

## 7. ТЗ: новые возможности

Ниже — предлагаемый backlog, а не уже согласованный набор изменений. Приоритет отражает предполагаемую полезность для работы с архивом. Все возможности сохраняют исходные фотографии; массовое редактирование касается каталога программы.

### FEATURE-01. Быстрый переход по Timeline — P2 / M

**Сценарий:** перейти к году, месяцу или дате, не прокручивая весь архив.

**Требования:** компактная навигация год → месяц → день; переход к ближайшему доступному дню с явной подписью, если выбранный день пуст. API навигации возвращает только даты/счётчики, без всех фотографий. Даты навигации соответствуют правилам обычной подборки; календарь не обещает открыть невидимый день, состоящий только из плохих оценок. URL сохраняет точку входа, Back возвращает прежнее место. Возможность «все дни, включая только bad» при необходимости проектировать отдельной настройкой.

**Приёмка:** переход к старому году не загружает промежуточные годы; обычный лимит 15, порядок оценок, Show all и Analyse сохраняются; фильтры Statistics не применяются. **Зависимости:** DB-01, WEB-01/03.

### FEATURE-02. Полнота и ошибки анализа в Directories — P2 / M

**Сценарий:** понять, какие каталоги готовы и почему часть фото не проанализирована.

**Требования:** сохранить существующие счётчики, добавить раскрываемые детали по стадиям EXIF/цвет/резкость/сигнатура. Для каждой стадии различать «ожидает», «успех», «ошибка», «не поддерживается»; NULL сам по себе недостаточен. Показывать время последнего прохода и доступность корня. Список проблемных файлов с причиной и действием повторного анализа после исправления причины. Пустые реально посещённые каталоги потребуют отдельного реестра каталогов; это отдельная часть задачи, поскольку сейчас дерево выводится из `photos`.

**Приёмка:** счётчики стадий сходятся с определёнными состояниями файлов; ошибка RAW объясняется; повтор можно ограничить каталогом/стадией. Refresh остаётся ручным, раскрытые ветви не сбрасываются. **Зависимости:** CODE-01/02/05, DB-02. Запуск прохода из веба требует общего координатора с launcher, чтобы не создать двух писателей; до него интерфейс только показывает диагностику.

### FEATURE-03. Сохранённые выборки и коллекции — P2 / M

**Сценарий:** вернуться к «лучшим снимкам отпуска» или набору для печати.

**Требования:** два явно различимых типа: сохранённый набор фильтров с динамическим результатом и коллекция конкретных photo ID. Имя, переименование, удаление, открытие в анализаторе, экспорт списка путей. Формат фильтров версионируется; поведение после обновления приложения определено. Привязка пользовательских данных к ID требует сохранения ID при сверке/переносе.

**Приёмка:** новые подходящие снимки появляются в сохранённой выборке; состав фиксированной коллекции сам не меняется. Удаление коллекции не удаляет фотографии. Оценки/теги продолжают работать в общей карточке. **Зависимости:** CODE-01/04, DB-02, WEB-01.

### FEATURE-04. Сравнение дубликатов и близких кадров — P2 / L

**Сценарий:** сравнить несколько снимков рядом и выбрать лучший.

**Требования первой версии:** сравнение 2–4 фото, связанный zoom/pan, размеры, время, рейтинг, резкость; отметки и добавление в коллекцию. Для групп явно показывать основание совпадения: имя/размер/дата, частичная сигнатура или полный hash. Не называть частичную сигнатуру доказательством побайтового равенства. Автоматическое удаление оригиналов не включать.

**Вторая версия, отдельное исследование:** похожие, но не идентичные кадры через perceptual hash; свой версионированный проход, порог и оценка ложных совпадений. Не менять этим существующее правило точных дубликатов.

**Приёмка:** переключение сравниваемого снимка сохраняет масштаб; оценка меняется везде после подтверждения сервера; отсутствующий файл объясняется; группировка соответствует указанному правилу. Для похожести нужен размеченный проверочный набор, а не только визуальная демонстрация. **Зависимости:** CODE-02, DB-03, WEB-01/02; коллекции — FEATURE-03 по необходимости.

### FEATURE-05. Перепривязка перенесённого архива — P2 / L

**Сценарий:** каталог переместили на другой диск, а оценки и теги нужно сохранить.

**Требования:** предварительный просмотр соответствий старый корень → новый корень; проверка относительных путей и файловых признаков, при неоднозначности — полный hash или ручное решение. Сохранить photo ID и аннотации; обновить path/folder и версию превью. При переименовании отдельных файлов не объединять записи только по частичной сигнатуре. Транзакционное применение, резервная копия и отчёт о неоднозначных/не найденных файлах.

**Приёмка:** перемещение тестового дерева сохраняет оценки, комментарии, теги и коллекции; конфликт путей не перезаписывает другую запись; отмена предварительного просмотра не меняет БД. Фото физически перемещает пользователь, операция меняет каталог программы. **Зависимости:** CODE-01/02, DB-02/05, WEB-02.

## 8. Порядок реализации

| Этап | Состав | Результат и условие завершения |

Выделение модулей делать постепенно внутри соответствующих этапов. Календарную оценку уточнить после этапа 0 и выбора объёма новых функций; суммировать S/M/L как человеко-дни нельзя.

## 9. Общая приёмка и измеримые ориентиры

Для сравнения использовать одинаковые машину, версии Python/SQLite, данные, seed, настройки и уровень фоновой нагрузки. Минимум 5 прогревочных и 30 измеряемых запросов для median/p95; холодные превью проверять отдельно. Наборы: 10 тыс./100 тыс./1 млн записей; 10 тыс. фото за день; 10 тыс. каталогов; много одинаковых taken; кириллица и спецсимволы; пропавший корень; параллельный писатель. Реальные файлы нужны только отдельному набору JPEG/RAW-тестов.

Предварительные цели для архива около 130 тыс. записей на контрольной машине:

| Метрика | Цель |
|---|---|
| Timeline: 8 дней, прогретая БД | p95 ≤ 250 мс; правильность подборки неизменна |
| Раскрытие дня: 200 записей | p95 ≤ 100 мс на обычном дне; большой день измеряется отдельно |
| Directories, текущий масштаб | p95 ≤ 500 мс |
| Statistics без кэша | median минимум вдвое меньше исходного; ориентир p95 ≤ 1,5 с для базовых сценариев |
| Обратная связь на действие в UI | состояние загрузки/нажатия видно за ≤ 100 мс |
| Прокрутка | нет систематических задач JS > 50 мс; проверка DOM и heap после длинной сессии |
| Повторное сканирование | прежняя корректность и ≥ 90% исходной пропускной способности до отдельной оптимизации |
| Сохранность | ноль потерянных аннотаций во всех сценариях сбоя, перепривязки и миграции |

Это цели разработки, не результаты уже выполненного нагрузочного теста. Если конкретная сортировка/фильтр не укладывается, она получает отдельный профиль и обоснованный бюджет, а не скрывается общей средней.

Каждое изменение принимается по сравнению корректности до/после, проверкам Windows/Linux, измерениям целевого сценария и отсутствию необъяснённых регрессий. Пользовательские изменения отражаются в README на двух языках и CHANGELOG. Миграции имеют проверенный путь резервного копирования/восстановления. Исходные фотографии, личные пути и координаты не включаются в тестовые артефакты репозитория.
